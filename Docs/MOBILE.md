# Kiorly Team: staff mobile app API (Kiorly Clinic)

Kiorly Team is the single staff app (Expo) for Clinic, Pharmacy and Lab. This file is the **Clinic side**: what the app calls, what was added for it, how it is gated and secured. Code: `apps/api/src/mobile/`. Tests: `mobile.node.test.ts` (pure), `mobile.integration.test.ts` (real DB). Demo logins: `Docs/TEST_DATA.md` ("Kiorly Team mobile"). All paths are under `/api/v1`.

## 1. Entitlement `mobile_staff_app` (commercial, NOT a safety control)
* A **PlanEntitlement** key in `src/entitlements/plans-matrix.ts` (`MODULE_ENTITLEMENT_KEYS`, `ENTITLEMENT_MIN_PLAN = PRO`, `PLAN_MATRIX`): `LITE` off, `PRO`, `CLINIC`, `ENTERPRISE` on; Nurse edition `NURSE_LITE` off, `NURSE_PRO` and `NURSE_AGENCY` on. Data migration `20261120160100_mobile_staff_app_entitlement` inserts the rows for deployed DBs; `ensurePlanEntitlements` (seed) keeps them in sync. `Docs/PLANS_AND_ENTITLEMENTS.md` matrix updated (a test keeps the doc and the matrix equal).
* Per-tenant override: the existing `TenantEntitlementOverride` (it is merged into the resolved entitlements, so support can grant or revoke per org).
* **Kiorex control plane**: `MobileEntitlementService` also honours the signed Kiorex flag snapshot for key `mobile_staff_app` (global / market / org `OFF`), reason `FLAG_OFF`. The key is **not** in `CLINIC_FLAG_DEFINITIONS` (that registry is pinned to `kiorex-contracts/flags/catalogue.json`); **TODO (cross-repo, NEEDS_HUMAN review):** add `mobile_staff_app` (class Module, scopes global/market/org, no dependencies, not launch-locked) to the catalogue so Kiorex super admin can list it. Until then the snapshot path simply never fires.
* Plan names are normalised for the app: `LITE`/`NURSE_LITE` -> `BASIC`; `PRO`/`CLINIC`/`NURSE_PRO` -> `PRO`; `ENTERPRISE`/`NURSE_AGENCY` -> `ENTERPRISE`. `org.rawPlan` carries the real key. A `SUSPENDED` subscription turns the entitlement off.
* **Safety alerts are never gated** (ADR-025): `mobile-alerts.service.ts` does not import the entitlement service (a test forbids it).

## 2. Enforcement (global `MobileInterceptor`)
It is an `APP_INTERCEPTOR` (runs after the controller `JwtAuthGuard`, so `req.user` exists; the existing `APP_GUARD` runs before auth and cannot be used).
1. **Device binding.** If `X-Kiorly-Device` (+ `X-Kiorly-Device-Token`) is present it must match an ACTIVE `MobileDevice` of the caller (token compared as sha256, constant time) else `401 {code:"DEVICE_REVOKED"}`. `lastSeenAt` is refreshed at most once a minute.
2. **Entitlement.** Every `/mobile/*` route and every request with `X-Kiorly-Client: kiorly-team/<ver>` needs the entitlement, else `403 {statusCode:403, code:"FEATURE_DISABLED", key:"mobile_staff_app", scope:"org", reason:"PLAN_BELOW_PRO"|"FLAG_OFF", message, messageAr}`. **Precedence:** the gate is the global `MobilePlanGuard` (`APP_GUARD`, verifies the bearer token itself because it runs before the controller `JwtAuthGuard`), so `FEATURE_DISABLED` beats every controller-level role/scope/entitlement 403 on app-flagged routes; `MobileInterceptor` keeps device binding and repeats the check as defence in depth.
   Exempt (open on every plan): `/auth/*`, `GET /mobile/bootstrap`, `/mobile/alerts*`, `POST /mobile/upgrade-request`, `DELETE /mobile/devices/:id`. Web traffic (no client header, not `/mobile/*`) is untouched.

### Modules per role (bootstrap `modules[].key`)
`clinic.schedule`, `clinic.patients`, `clinic.visits` (start/notes), `clinic.prescriptions`, `clinic.labs`, `clinic.vitals`, `clinic.homevisits`, `clinic.revenue`. Physician: all clinical, no revenue. Nurse: schedule, patients, vitals, home visits (incl. sample collection); **no `clinic.labs`**: Lab results is the physician's result-review queue (read and approve finished values), a nurse in the field needs rounds, vitals, the patient summary and safety, so `GET /mobile/lab-results` answers 403 `MODULE_NOT_ALLOWED` for role NURSE and for profession NURSE/ASSISTANT accounts (Nurse edition solo/agency staff). Web is unchanged: a nurse still sees the orders of the patient being charted in the encounter. Receptionist/call centre: schedule + patients; in the NURSE edition (agency dispatcher, e.g. `dispatch@nurse-demo`) also `clinic.homevisits` (no visits, prescriptions, labs or vitals). Branch manager/CLINIC_ADMIN: schedule, patients, vitals, revenue. Finance: schedule + revenue. Group admin/supervisor/owner: everything. `clinic.homevisits` is also on for every clinical role in the NURSE edition. Profession NURSE/ASSISTANT never gets visits/prescriptions even with the PHYSICIAN role (Nurse edition solo/agency staff carry role PHYSICIAN + profession NURSE).

### Safety alert kinds (`GET /mobile/alerts`; ids are `<prefix>_<rowId>`)
`hv_` `HOME_VISIT_SOS` (CRITICAL), `HOME_VISIT_MISSED_CHECKIN` (HIGH, `NO_ANSWER`), `NURSE_SAFETY` (HIGH, `UNSAFE_ABORT`) from `HomeSafetyAlert` (ack sets `acknowledgedAt`, status ACKNOWLEDGED); `vit_` `CRITICAL_VITALS` from `VitalsObservation.critical` with no escalation (ack records the escalation entry); `lab_` `CRITICAL_LAB_RESULT` (an order item flagged `CRITICAL*`, acknowledge is separate from approve). Managers/owners see all; a clinician sees only alerts of own visits/readings. 14-day window. Roles: GROUP_ADMIN, GROUP_SUPERVISOR, BRANCH_MANAGER, CLINIC_ADMIN, PHYSICIAN, NURSE (+ tenant owner). Nurse-edition dispatchers (RECEPTIONIST / CALL_CENTER in a NURSE-edition org) see and acknowledge the org's `hv_` home-visit alerts (SOS, missed check-in, NURSE_SAFETY) only, never vitals or lab alerts; they may also read `GET /home-visits/safety-alerts` on the web API (ack/resolve stay manager-only).

### Mock push (`MOBILE_PUSH_MODE=mock`, default)
`MobilePushService` stores bilingual messages in `MobilePush` (= the inbox) as DELIVERED; `real` is refused until the provider go-live pass (`Docs/NEEDS_HUMAN.md`). Hooks (informational, never throw): home-visit safety alert raised (`HOME_SAFETY_ALERT`, SAFETY, to managers/owners + the clinician, not plan-gated), patient checked in (`PATIENT_CHECKED_IN`), lab results ready (`LAB_RESULT_READY`), critical vitals (`CRITICAL_VITALS`). Templates carry no clinical values. Mirrors are only stored for staff who exist; there is no remote delivery in mock mode.

## 4. Authentication
* Staff sign in with **product login**: `POST /auth/login {email,password,mfaCode?}` -> `{accessToken (JWT, short-lived), refreshToken, sessionId, user}`; `POST /auth/refresh {refreshToken}` rotates both; `GET /auth/me`; `POST /auth/sessions/revoke-all`. MFA: privileged roles may need `mfaCode` (`MFA_SETUP_REQUIRED` after the 7-day grace).
* **Passport OIDC (PKCE)**: Kiorly Clinic already has the confidential `kiorly-clinic` client seam (KCV-201: `/auth/kiorex/start|callback|complete`, edition-aware KNED redirect). It exchanges codes server-side and needs a client secret, so it is a **web** flow. For the native app a public PKCE client (`kiorly-team`, redirect `kiorlyteam://auth/callback`) must first be registered in `kiorex-account` (NEEDS_HUMAN) and the API must accept its audience; until then the app uses product login. Device binding + remote sign-out work identically for both.
* Device-bound session flow: login -> `POST /mobile/devices` (token shown once, stored in SecureStore) -> send `X-Kiorly-Client`, `X-Kiorly-Device`, `X-Kiorly-Device-Token` on every call -> `401` (revoked session or `DEVICE_REVOKED`) = wipe local session.

## Offline replay of home-visit transitions
`depart`, `arrive`, `finish` and `abort-unsafe` are idempotent for the assigned clinician: when the visit is already in the target state the answer is `200` with the current visit plus `replayed:true`, with no new geostamp/event/alert/push (the offline queue can treat it as done). A transition that is genuinely illegal from the current state (for example `depart` after `ARRIVED`) is still `409 ILLEGAL_TRANSITION`; another user still gets `403`.
